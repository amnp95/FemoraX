## 1. Methods: DOF elimination (master-slave transformation), Lagrange multipliers, penalty, augmented Lagrangian, Nitsche; accuracy, conditioning, iterative solvers

### Takeaway
For linear constraints of the form u_s = T u_m (equalDOF, rigid links, rigid diaphragms), exact elimination (reduced operator T^T K T, T^T M T) is the only method that adds no stiffness, no unknowns and no saddle point. That makes it the natural fit for matrix-free CG and for explicit integration. Penalty brings in an extra stiffness that both ruins conditioning and lowers the explicit stable step. Lagrange multipliers give an indefinite saddle-point system, which is bad for CG. OpenSees recommends Transformation for rigidDiaphragm. Its implementation uses small-rotation, constant T matrices built from the initial coordinates.

### Cited Findings
- OpenSees documentation recommends the Transformation constraint handler for rigidDiaphragm ("To enforce this constraint, Transformation constraint handler is recommended"). The command takes the perpendicular direction, the retained node and the constrained nodes, and works for ndf=6 in 3D and ndf=3 in 2D. — [OpenSeesPy rigidDiaphragm](https://openseespydoc.readthedocs.io/en/latest/src/rigidDiaphragm.html); [OpenSees docs rigidDiaphragm](https://opensees.github.io/OpenSeesDocumentation/user/manual/model/mp_constraint/rigidDiaphragm.html); [OpenSees wiki](https://opensees.berkeley.edu/wiki/index.php/RigidDiaphragm_command)
- The OpenSees manual cites Cook on the trade-offs. Penalty functions "introduce no new variables", but the penalty numbers must be "large enough to be effective but not so large as to provoke numerical difficulties". Lagrange multipliers are "more attractive than the transformation method if there are few constraint equations that couple many DOF". — [OpenSees user manual (constraint handlers)](https://opensees.berkeley.edu/OpenSees/manuals/usermanual/617.htm) (manual page as surfaced by search; the exact page number of the quote was not confirmed)
- OpenSees forum users disagree about which handler rigidDiaphragm needs: one poster believed Lagrange was required. The thread does not resolve it. — [OpenSees forum, "Trouble with Rigid Diaphragm"](https://opensees.berkeley.edu/community/viewtopic.php?p=117208)
- OpenSees `RigidDiaphragm` and `RigidBeam` (rigidLink beam) build a constant constraint matrix from the initial coordinate differences. Diaphragm in xy with ndf=6: constrained DOFs (0,1,5), `mat(0,2) = -deltaY`, `mat(1,2) = deltaX`. RigidBeam fills the full small-rotation skew matrix (`mat(0,4)=deltaZ`, `mat(2,4)=-deltaX`, `mat(1,3)=-deltaZ`, `mat(2,3)=deltaY`, ...). These are linearised (small-rotation) rigid kinematics, not geometrically exact ones. — local source `../OpenSees/SRC/domain/constraints/RigidDiaphragm.cpp` lines 160-185 and `RigidBeam.cpp` lines 124-154, commit 955ceb0a5
- OpenSees has four constraint handlers: Plain, Penalty, Lagrange, Transformation, plus Auto. — local source `../OpenSees/SRC/analysis/handler/` (commit 955ceb0a5)
- FemoraX's own audit of the OpenSees Transformation handler found patterns that it silently mishandles, for example a node constrained by more than one equalDOF command (only the first MP per constrained node is applied). FemoraX refuses these. — local `docs/deviations.md`, "Constraint handling — refuse what OpenSees' Transformation handler silently gets wrong" (OpenSees `TransformationConstraintHandler.cpp`, `TransformationDOF_Group.cpp`, 955ceb0)
- Abaqus/Standard usually imposes kinematic constraints by eliminating DOFs at the dependent nodes, and it sorts constraints into an elimination order. Abaqus/Explicit has no ordering requirement and solves all kinematic constraints simultaneously, except those from kinematic contact. — [Abaqus "Kinematic constraints: overview" (2016)](https://ceae-server.colorado.edu/v2016/books/usb/pt08ch35s01abo32.html); [Abaqus 2017 "About Kinematic Constraints"](https://abaqus-docs.mit.edu/2017/English/SIMACAECSTRefMap/simacst-c-kinematic.htm) (the 2017 page returned HTTP 410 on direct fetch; content as reported in search snippets)
- Abaqus/Explicit always uses a geometrically nonlinear formulation to enforce kinematic constraints, even in steps declared geometrically linear. — same Abaqus kinematic constraints overview pages as above
- MFEM handles nonconforming (hanging-node) meshes the same way: it assembles the full system regardless of non-conformity, builds a prolongation P from the conforming (true) DOFs to all DOFs, and solves the problem restricted to the conforming DOFs (P^T A P, with P^T b). — [arXiv 2511.20142 (contact mechanics with AMR in MFEM)](https://arxiv.org/pdf/2511.20142); [MFEM: a modular finite element methods library](https://arxiv.org/pdf/1911.09220)

### Inferences
- The general linear MPC u = T q (T maps the retained "true" DOFs q to all DOFs) gives the reduced dynamics T^T M T q'' + T^T f_int(Tq) = T^T f_ext. This has the same form as MFEM's conforming prolongation and deal.II's AffineConstraints. FemoraX's union-find equalDOF numbering is the special case where every row of T is a unit vector. A rigid link or diaphragm adds rows with entries (1, ±r). **[textbook, not verified this session: Cook et al., Concepts and Applications of FEA, ch. 9; Belytschko, Liu & Moran, Nonlinear Finite Elements for Continua and Structures, 2nd ed. 2014]**
- Elimination keeps symmetry and positive definiteness: T^T K T is SPD when K is SPD on the range of T. So CG and the Jacobi diagonal keep working. Penalty adds k_p C^T C with k_p >> K, which raises the condition number roughly in proportion to k_p / k_struct, and that hurts CG. This agrees with the FemoraX design note that "penalty ruins iterative-solver convergence". Lagrange multipliers give [K C^T; C 0], which is indefinite: CG cannot be used directly, and GMRES or MINRES with a block preconditioner is needed. **[textbook, not verified this session]**
- Augmented Lagrangian (Uzawa iterations on top of a moderate penalty) gives exact constraints with bounded k_p, at the cost of an outer iteration. It suits contact far more than fixed linear MPCs, which elimination satisfies exactly for free. Nitsche's method is aimed at interface coupling of non-matching meshes and embedded or immersed interfaces, not at rigid links. Its stabilisation term behaves like a mesh-dependent penalty (~ E/h) and also enters the explicit stable step. **[textbook, not verified this session]**
- OpenSees' constant, small-rotation T for rigidLink and rigidDiaphragm is adequate for small-rotation earthquake analysis. Large rotations (collapse, P-Delta of rigid offsets) would need the geometrically nonlinear enforcement that Abaqus/Explicit always uses (T updated with the current rotation). Matching OpenSees means a constant T, and a future large-rotation option would be a documented deviation.

## 2. Explicit codes: LS-DYNA, Abaqus/Explicit, EUROPLEXUS, Radioss — rigid bodies, MPCs, time step

### Takeaway
Production explicit codes keep the nodal mass diagonal and treat rigid bodies and kinematic MPCs as a separate small system:
1. Each rigid body gathers the forces and masses of its nodes into one 6-DOF body with a 6x6 inertia (translation plus a 3x3 inertia tensor about the centre of mass).
2. The body is integrated.
3. The nodal velocities are rebuilt from v = v_cm + omega x r.

Kinematic (non-penalty) rigid constraints add no stiffness, so they do not lower the stable step. Abaqus states that rigid bodies do not affect the global time increment. Penalty-enforced constraints do lower it. Abaqus weights its fallback penalties by the nodal masses and the stable increment so that they do not.

### Cited Findings
- Abaqus/Explicit: "rigid bodies and elements that are part of a rigid body do not affect the global time increment", so a rigid body in a stiff region allows a larger increment than a deformable mesh there. — [Abaqus/Explicit doc, contact troubleshooting / modeling considerations (2017)](https://abaqus-docs.mit.edu/2017/English/SIMACAEITNRefMap/simaitn-c-expcontacttrouble.htm) (as surfaced by search)
- Abaqus/Explicit: "the entire rigid body must possess mass and inertia unless constraints are used". The explicit scheme "requires nodal mass or inertia to exist at all activated degrees of freedom" unless those DOFs are constrained by boundary conditions. Massless springs, dashpots and connectors need "care ... either to constrain the node or to add mass and inertia". — [Abaqus 2025 "Explicit Dynamic Analysis"](https://docs.software.vt.edu/abaqusv2025/English/SIMACAEANLRefMap/simaanl-c-expdynamic.htm)
- Abaqus/Explicit stable increment: dt ≤ 2/omega_max. The element-by-element estimate is conservative. "Constraints such as boundary conditions and kinematic contact have the effect of compressing the eigenvalue spectrum", and the element-by-element estimates "do not take this into account". The global estimator usually allows larger increments, but it is not used with beams, thick shells, dashpots, material damping or subcycling, among others. — [Abaqus 2025 "Explicit Dynamic Analysis"](https://docs.software.vt.edu/abaqusv2025/English/SIMACAEANLRefMap/simaanl-c-expdynamic.htm)
- Abaqus/Explicit: implicit enforcement of constraints "can degrade performance for situations with overlapping constraints". — [Abaqus 2025 "Explicit Dynamic Analysis"](https://docs.software.vt.edu/abaqusv2025/English/SIMACAEANLRefMap/simaanl-c-expdynamic.htm)
- Abaqus/Explicit kinematic constraints:
  - Constraint forces appear as "nodal acceleration corrections at increment i".
  - A penalty method is used in some cases, for example tie slave nodes that also appear in other constraints. "The penalties are weighted based on the masses of nodes participating in the constraint and the stable time increment."
  - Overlapping, non-orthogonal constraints overconstrain the model, and "the resulting solution will be quite noisy". Except for rigid bodies, Abaqus/Explicit does not prevent this.
  - A kinematic contact constraint usually overrides a kinematic constraint on the same node.
  - Initial velocities of a constrained set are replaced by the mass-weighted average translational velocity and a rotational velocity about the centre of mass, and each node's velocity is recomputed from those.

  — [Abaqus "Kinematic constraints: overview" v2016](https://ceae-server.colorado.edu/v2016/books/usb/pt08ch35s01abo32.html); [Abaqus 2025 "About Kinematic Constraints"](https://docs.software.vt.edu/abaqusv2025/English/SIMACAECSTRefMap/simacst-c-kinematic.htm) (content from search snippets; direct fetch of the 2017 page failed)
- Abaqus/Explicit: MPCs on nodes of an active kinematic contact surface can create conflicting constraints. These are fine if the constraints are orthogonal and noisy if not. The penalty contact algorithm "introduces additional stiffness ... [that] can influence the stable time increment". — [Abaqus "Contact Constraint Enforcement Methods in Abaqus/Explicit" 2025](https://docs.software.vt.edu/abaqusv2025/English/SIMACAEITNRefMap/simaitn-c-expcontactconstraints.htm); [Abaqus contact troubleshooting 2017](https://abaqus-docs.mit.edu/2017/English/SIMACAEITNRefMap/simaitn-c-expcontacttrouble.htm)
- LS-DYNA `*CONSTRAINED_NODAL_RIGID_BODY` (CNRB) takes a node set, an optional centre-of-gravity node, optional inertia tensor terms (IXX ... IZZ) through the _INERTIA option, and initial velocities. With _INERTIA, LS-DYNA disregards the computed mass properties. — [Altair (Radioss reader of LS-DYNA keywords) CNRB page](https://help.altair.com/hwsolvers/rad/topics/solvers/rad/constrained_nodal_rigid_body_lsdyna_r.htm); [Ansys/DYNAmore webinar "LS-DYNA Rigid Bodies" (2019, PDF)](https://lsdyna.ansys.com/wp-content/uploads/2025/11/191119_Webinar_LS-DYNA_Rigid_Bodies.pdf) (webinar content as summarised by search; the PDF itself was not machine-readable here)
- LS-DYNA computes 6 rigid-body DOFs per rigid body (MAT_RIGID part), so disjoint element groups with the same part ID move together. Two rigid bodies cannot share nodes unless they are merged (`*CONSTRAINED_RIGID_BODIES`). — [MAT_020 theory notes (Scribd excerpt)](https://www.scribd.com/document/691952172/Mat-021-Theory) (aggregator, low confidence); [DYNAmore webinar](https://lsdyna.ansys.com/wp-content/uploads/2025/11/191119_Webinar_LS-DYNA_Rigid_Bodies.pdf)
- LS-DYNA error 30186 reports a rigid body whose inertia tensor is too small, which "could cause numerical instability in the rigid body subroutines". The workaround is `*CONTROL_RIGID` NORBIC=1. Single-node nodal rigid bodies are deleted; use `*ELEMENT_MASS` or `*ELEMENT_INERTIA` instead. — [Ansys Innovation Space knowledge article](https://innovationspace.ansys.com/knowledge/?p=165150) (forum/knowledge-base, medium confidence)
- The DYNAmore rigid-body webinar notes that unexpected rigid-body motion can come from too large a time step, and cancellation errors in rotations from too small a one. A model with no deformable bodies needs its time step set manually, because rigid bodies give no element step. — [DYNAmore webinar (as summarised by search)](https://lsdyna.ansys.com/wp-content/uploads/2025/11/191119_Webinar_LS-DYNA_Rigid_Bodies.pdf)
- The LS-DYNA Theory Manual has a "Rigid Body Motion" chapter (section 9.5 in the 2006 edition) with the rigid-body update equations. — [LS-DYNA Theory Manual 2006 (DYNAmore)](https://dynamore.de/de/download/manuals/ls-dyna/ls-dyna-theory-manual-2005-beta); [LS-DYNA Theory Manual R14 (Ansys)](https://ansyshelp.ansys.com/public/Views/Secured/Doc_Assets/Release/v242/LS-DYNA_Manual_Theory_R14.pdf) (not read: equations not extracted)
- EUROPLEXUS (JRC/CEA explicit fast-transient code) treats constraints, including complex contact-impact, mainly by Lagrange multipliers on velocities ("velocity-based constraints"), and also offers penalty. The JRC report "On the Parametrization of Velocity-Based Constraints in EUROPLEXUS" (Casadei, Markovic, Larcher; EUR 31504 EN, 2023, doi:10.2760/71283) documents this, and a companion report covers eliminating redundant constraints. — [JRC repository](https://publications.jrc.ec.europa.eu/repository/handle/JRC143268); [TRID record](https://trid.trb.org/View/2169506) (full text not read: the PDF link returned 404)

### Inferences
- How explicit codes integrate a rigid body (consistent with the Abaqus statements above):
  1. Each step, sum the nodal internal and external forces of the body's nodes into a resultant force F and a moment M about the centre of mass.
  2. Solve m a_cm = F and I omega' + omega x I omega = M. I is 3x3 per body, so a 6x6 block that is inverted or diagonalised in principal axes, cost O(1) per body.
  3. Integrate.
  4. Set every slave node's velocity to v_cm + omega x r and update r.

  The global nodal mass stays diagonal. The body's 6x6 inertia lives outside the global vector and is never assembled into it. **[textbook, not verified this session: Belytschko, Liu & Moran 2014 ch. 6 (explicit) and the LS-DYNA Theory Manual "Rigid Body Motion"; Benson & Hallquist, "A simple rigid body algorithm for structural dynamics programs", IJNME 22 (1986) 723-749 — citation from memory, not verified]**
- Kinematic rigid constraints remove the internal relative motion between the slaves, which can only remove high frequencies (constraint compresses the spectrum; Abaqus quote above). Elements whose nodes all belong to one rigid body have no deformation and can be skipped in the stable-step estimate. An element with some rigid and some free nodes keeps an element estimate that stays conservative only if the mass partition assigned to the element is valid. This matters for FemoraX's element eigenvalue bound: after reduction, the master's mass includes the slaves' masses and the rotational inertia m r^2. The bound then needs each element's share of the reduced (block) mass, or else it must use the unreduced nodal masses, which is conservative by constraint monotonicity.
- Penalty-enforced links in explicit codes: a penalty spring k_p between nodes of mass m gives omega^2 ≈ k_p (1/m_1 + 1/m_2), hence dt ≤ 2/omega. That is why Abaqus scales its fallback penalties with the nodal masses and the stable increment: it chooses k_p ≈ c m / dt^2 so that the penalty never sets the step. FemoraX could do the same for any future penalty interface, at the cost of a constraint that is satisfied only approximately.
- EUROPLEXUS-style Lagrange multipliers in explicit dynamics need a solve of C M^-1 C^T lambda = rhs each step. That is cheap when the constraints are decoupled (block diagonal) and expensive when they overlap, consistent with Abaqus' warning that implicit enforcement degrades performance for overlapping constraints. **[the exact EUROPLEXUS equations were not read]**

## 3. Rigid floor diaphragms in earthquake-engineering codes (explicit vs implicit); known issues

### Takeaway
In OpenSees, rigidDiaphragm is a constant small-rotation transformation (ux, uy, θz of each slave follow the master). With Transformation and an explicit integrator, the reduced mass T^T M T has off-diagonal translation-rotation coupling terms (−m Δy, m Δx). OpenSees' DiagonalSOE either drops them (default: only the diagonal) or row-sums them (`-lumped`). Either way the rigid-body inertia is exact only when the master node sits at the floor's centre of mass. I found no documentation of this in the OpenSees docs: it is a finding from the source. Commercial programs (ETABS, SAP2000, Perform-3D) were not covered by any fetched source.

### Cited Findings
- `DiagonalSOE::addA` (used by the explicit integrators' `system Diagonal`) adds only `m(i,i)` to the diagonal unless `lumpDiagonal` is set. In that case it adds the full column sum `sum_j m(j,i)`. `lumpDiagonal` defaults to false and is set by `system Diagonal -lumped`. — local source `../OpenSees/SRC/system_of_eqn/linearSOE/diagonal/DiagonalSOE.cpp` lines 179-230 and `DiagonalDirectSolver.cpp` lines 46-54, commit 955ceb0a5
- `DiagonalDirectSolver::solve` stops on a zero diagonal (`aii == 0.0`). — local source `DiagonalDirectSolver.cpp` lines 108-112, commit 955ceb0a5
- `TransformationFE::getTangent` transforms the element's full tangent (for an explicit integrator this is the mass-weighted matrix) by the constraint matrices T: T^T (.) T. — local source `../OpenSees/SRC/analysis/fe_ele/transformation/TransformationFE.cpp` lines 292-410, commit 955ceb0a5
- The OpenSees examples manual uses a Transformation handler for its rigid-diaphragm building model "due to the presence of the multi-point constraints". — [OpenSees Examples Manual](https://opensees.berkeley.edu/OpenSees/manuals/ExamplesManual/HTML/800.htm)
- OpenSees forum threads on the rigid diaphragm show users unsure how it is implemented ("Theoretical implementation of rigid diaphragm") and having convergence trouble with it. — [forum p=103144](https://opensees.berkeley.edu/community/viewtopic.php?p=103144); [forum p=117208](https://opensees.berkeley.edu/community/viewtopic.php?p=117208)
- FemoraX's own design records that OpenSees beams give no rotational mass, and that OpenSees' explicit integrators refuse a massless DOF (`DiagonalDirectSolver`: "aii = 0"). Femora therefore writes element masses, including scaled rotational masses, as nodal masses. — local `docs/design.md`, "Structures: mass and damping standard"

### Inferences
- A slave of mass m at offset (Δx, Δy) from the master contributes the following to the master's reduced mass in (ux, uy, θz):
  ```
  [ m      0     -mΔy ]
  [ 0      m      mΔx ]
  [ -mΔy   mΔx    m(Δx²+Δy²) ]
  ```
  OpenSees' default diagonal solver keeps [m, m, m r²] and drops the couplings. That is exact only when Σ m Δx = Σ m Δy = 0, i.e. the master at the centre of mass. Femora and OpenSees users usually place the master node at the centre of mass, which hides the problem. With `-lumped`, OpenSees adds m − mΔy to the ux diagonal: this mixes units (mass and mass·length) and is not physically meaningful. FemoraX should not reproduce either behaviour. It should either invert the exact small block per rigid group (a 3x3 for a diaphragm, 6x6 for a rigid body) or require/report the centre-of-mass condition, and record the difference in `docs/deviations.md`. **[derived from the OpenSees source above. Not run in OpenSees this session: a two-node test would confirm it.]**
- In implicit Newmark, OpenSees' Transformation path is exact (T^T M T is assembled in full), so explicit and implicit OpenSees runs of the same diaphragm model can differ when the master is off the centre of mass. This is a useful verification case for FemoraX.
- Penalty diaphragms (or very stiff in-plane slab shells used in place of a constraint) put an in-plane slab frequency into the explicit spectrum, and that frequency sets the step. A kinematic diaphragm removes it. This is the main argument for exact elimination plus small block inertia in FemoraX's explicit stage.

## 4. Constraints in matrix-free and GPU codes (deal.II, MFEM/libCEED); multi-GPU

### Takeaway
Matrix-free libraries apply constraints as a prolongation fused into the element gather and scatter. deal.II's `FEEvaluation::read_dof_values` resolves constraints while gathering, and `distribute_local_to_global` applies the transpose while scattering. Constrained rows get an identity block so that CG sees a nonsingular operator. MFEM solves on "true" (conforming) DOFs through a prolongation P and its transpose. Munch, Ljungkvist and Kronbichler split hanging-node constraints into a special on-the-fly operator plus a generic one, and cut the extra cost of constrained cells 5-10x on CPU. FemoraX's per-element equation maps already are this prolongation for unit-row T. Rigid links would add a few weighted rows.

### Cited Findings
- deal.II step-37:
  - In the matrix-free cell loop, `FEEvaluation` reads the source values "including the resolution of constraints" and writes back with `distribute_local_to_global`, named after the `AffineConstraints` function.
  - Constrained DoFs get no contribution, so their rows and columns are zero. `MatrixFreeOperators::Base` sets that block to identity so that CG has a nonsingular matrix.
  - `compute_diagonal()` sets the constrained entries to one. With hanging nodes, the diagonal computed element-wise "lumps" some of the constrained contributions: correct up to discretisation accuracy but not the exact diagonal.
  - MPI: `cell_loop` calls `update_ghost_values()` on the source and `compress(add)` on the destination.

  — [deal.II step-37 tutorial](https://dealii.org/current/doxygen/deal.II/step_37.html)
- In assembled deal.II code, hanging nodes work as long as local contributions go through `AffineConstraints::distribute_local_to_global`. A user reported trouble with a hanging node on an edge shared across MPI ranks. Inhomogeneous constraints keep stale values if boundary data change, so the constraints must be rebuilt. — [deal.II mailing list 2025](https://groups.google.com/g/dealii/c/B5IJB1O-BSw); [deal.II mailing list 2023](https://www.mail-archive.com/dealii@googlegroups.com/msg14064.html)
- Munch, Ljungkvist & Kronbichler, "Efficient application of hanging-node constraints for matrix-free high-order FEM computations on CPU and GPU" (ISC High Performance 2022, LNCS): the constraints are resolved on the fly and split into a hanging-node operator and a generic operator for other constraints (Dirichlet). The interpolation step differs between CPU and GPU. On CPUs the extra cost of constrained cells drops by a factor of 5-10 for high-order Laplace on affine meshes. — [Augsburg repository record](https://opus.bibliothek.uni-augsburg.de/opus4/frontdoor/index/index/year/2022/docId/99791); [abstract at publications.hzg.de](https://publications.hzg.de/id/50655/index.php); [Munch dissertation](https://opus.bibliothek.uni-augsburg.de/opus4/files/109862/Munch_Dissertation.pdf)
- Earlier work by the same group: a GPU matrix-free geometric multigrid with hanging nodes, about 1.5-2x faster than a multicore CPU on a P100. — [Crossref record, doi:10.1145/3322813](https://api.crossref.org/works/10.1145%2F3322813)
- MFEM's partial-assembly operator is a product of factors, including P (T-vector to L-vector: the parallel and conforming prolongation), G (L-vector to element E-vector) and the quadrature operator. The factors are usually not stored as sparse matrices. — [End-to-end GPU acceleration of LOR preconditioning (arXiv 2210.12253)](https://arxiv.org/pdf/2210.12253); [MFEM paper (arXiv 1911.09220)](https://arxiv.org/pdf/1911.09220)
- MFEM supports conforming and non-conforming AMR with arbitrary-order hanging nodes, and partial assembly and sum factorisation are implemented in the integrators. — [MFEM paper (arXiv 1911.09220)](https://arxiv.org/pdf/1911.09220)

### Inferences
- For FemoraX, the cleanest matrix-free form of a general linear MPC is the prolongation: y = T^T A_elem (T x). Today T is a pure index map (each element DOF maps to one equation or −1), so it is applied for free by the gather and scatter maps.
- **Option A (master-only equations):** a rigid link or diaphragm slave DOF becomes a short linear combination: u_s = u_m + θ_m × r, i.e. up to 3-4 terms per slave DOF. The element kernel's gather would read (equation, weight) lists instead of single equations. The scatter is the transpose, deterministic through the existing gather (slot) scatter. This is what deal.II does, at the cost of variable-length maps (memory, divergence on GPUs).
- **Option B (cheaper on GPUs):** keep elements gathering full nodal values. Before the element pass, expand the master values to slave nodal vectors with one small kernel (u_s = T u_m). After the force pass, contract the slave forces onto the masters with another small kernel (f_m += T^T f_s), in a fixed order for determinism. The element kernels stay unchanged. The extra traffic is proportional to the number of constrained nodes, a tiny fraction in soil-structure models.
- Explicit stage: Option B plus a per-group block solve (3x3 diaphragm or 6x6 rigid body, precomputed and inverted once per stage, since T is constant) gives exact rigid-body dynamics with a diagonal mass everywhere else. Implicit stage: the operator becomes T^T K T for CG with no other change. The Jacobi diagonal of the master DOFs needs the T-weighted element diagonals plus off-diagonal cross terms. deal.II's note that an element-wise diagonal with constraints is only approximate applies here: compute the master's diagonal exactly from the small group, or accept an approximate diagonal, which is fine for a preconditioner.
- Multi-GPU: a rigid diaphragm couples a whole floor. With METIS partitions this can cross subdomains. The FemoraX plan (the owner of the retained node resolves the tie; constrained nodes become ghosts of that subdomain) extends to diaphragms. The master's group force is a reduction over the ranks that hold its slaves: one 3- or 6-vector per group per step, cheap. Alternatively, Femora/METIS could weight the partition so that a floor stays in one subdomain.

## 5. Interaction with multi-rate / local time stepping (LTS) and subcycling

### Takeaway
No published LTS analysis covers general linear MPCs or rigid bodies. The safe rule is the one FemoraX already applies: a constraint group (union-find group, rigid body or diaphragm, now with its master) lives entirely in one level, the finest of all elements touching any of its DOFs. Abaqus disables its global time-step estimator with subcycling, and Abaqus' own subcycling and rigid-body statements give no further rules (not found).

### Cited Findings
- Abaqus/Explicit does not use the global stable-time estimator with subcycling, beams, thick shells, dashpots or material damping, among others. — [Abaqus 2025 "Explicit Dynamic Analysis"](https://docs.software.vt.edu/abaqusv2025/English/SIMACAEANLRefMap/simaanl-c-expdynamic.htm)
- The FemoraX LTS plan states that DOF elimination merges a constraint group into one equation, so a group sits in one level by construction. The LTS step 2 test found that laminar-boundary ties pull the elements around a whole tied perimeter into a fine element's level. The published LTS analyses cover linear operators only, and constraints spanning levels are "not covered by any published analysis". — local `docs/design.md`, "Local time stepping"
- The Diaz-Grote / Grote-Michel-Sauter stabilised leapfrog LTS is formulated for M u'' + A u = f with M diagonal (lumped). — [Grote, Michel & Sauter, Math. Comp. 2021, arXiv:2005.13350](https://arxiv.org/abs/2005.13350) (as cited in FemoraX design.md; not re-read this session)

### Inferences
- With exact elimination, the reduced system is T^T M T q'' + T^T A T q = T^T f. A rigid group has a small dense mass block instead of a diagonal entry. The LTS recurrences apply M^-1 per level. A block-diagonal M (diagonal everywhere except small, non-overlapping group blocks) can be inverted exactly block by block, so the scheme's structure (A Pi_f, level-wise M^-1) carries over unchanged as long as each block lies in one level. The energy argument of Diaz-Grote needs M symmetric positive definite and A symmetric, and both hold under T^T(.)T. The derivation should be checked for block M rather than assumed. **[inference, not verified in the papers]**
- Level assignment: a rigid body or diaphragm transmits force instantly across its whole extent, so every element touching any slave node is in the group's level. A floor diaphragm on a building in a fine level pulls all the floor's beams and columns, and any soil touching the slaves, into that level. This repeats the laminar-boundary finding at structural scale. Keeping diaphragms on the structure only (not on soil nodes) bounds the cost.
- A kinematic rigid body itself has no element stable step, so its level is set only by the deformable elements attached to it. A penalty-enforced link would set its own (often finest) level through omega² ≈ k_p/m. This is another reason to prefer elimination.
- Subcycling with rigid bodies in commercial codes: no source found. The inference is that the body is integrated at the step of the finest attached element.
